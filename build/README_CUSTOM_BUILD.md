## چه چیزی تغییر کرده؟
فقط **دو فایل داخل rootfs** جایگزین شده‌اند؛ بقیهٔ ۲۸,۴۳۶ فایل و کل هدر/پارتیشن‌های دیگر **بایت‌به‌بایت** با اصل یکسان‌اند (اثبات‌شده در `tools/verify_custom.py`).

### ۱) `/usr/bin/bianbiang.sh` (mode 755)
- **ISSUE-001** — افزودن `while true` **respawn loop** دور اپ اصلی: هر crash/OOM/exit code 3 → راه‌اندازی مجدد UI به‌جای صفحهٔ سیاه دائمی.
- **ISSUE-002** — تابع `supervise()` برای نظارت بر `satipclient`، `app_console`، `streamrelay`: اگر بمیرند دوباره بالا می‌آیند.
- **ISSUE-003** — `apply_vm_tuning()` (تنظیم مستقیم `/proc/sys/vm/*`) + `setup_zram()` (فعال‌سازی swap فشرده در RAM، متناسب با حجم واقعی رم، سقف 256M، با fallback بی‌صدا اگر ماژول zram نبود).
- **ISSUE-005** — رفع باگ کپی‌پیست unmount: حالا هر `UD1/UD2/UD3` mount-point خودش حذف می‌شود.

### ۳) تغییر SW version (بلوک‌های softwareinfo) — `1.00.92` → `1.00.93`
منبع واقعیِ نمایشِ SW version در **System Information**، رشتهٔ داخل باینری نبود، بلکه یک **بلوک softwareinfo** با ساختار زیر است:
```
"IP" magic ... 1.00.00 (HW) ... 1.00.92 (SW) ... 3798 (build) ... MV300 (chipset) ... DDR 1GB ... TOP 8GB
```
این بلوک **سه نسخه** دارد و همه به `1.00.93` تغییر کردند (فقط بایت `2`→`3`):
| آفست | محل | نقش |
|------|-----|-----|
| `0x28` | HEADER بلوک ۱ | متادیتای upgrade |
| `0x434` | HEADER بلوک ۲ | متادیتای upgrade |
| `0x1BE322` | انتهای پارتیشن **logo** | **همان بلوکی که در زمان اجرا خوانده و نمایش داده می‌شود** |

- تأیید شد در ناحیهٔ قبل از rootfs **دقیقاً ۳ بایت** تغییر کرده و بقیه بایت‌به‌بایت اصل است.
- پارتیشن‌های header/logo فاقد checksum‌اند (flags `0x01000000`، low24=0) → ویرایش امن.

> **نکتهٔ رم (تصحیح مهم):** رشتهٔ `DDR 1GB` در این بلوک فقط یک **برچسب پیش‌فرض/توصیفی** است، **نه** اندازهٔ واقعی رم نصب‌شده. بررسی `bootargs` نشان داد bootloader **چند پروفایل حافظه** دارد و هنگام بوت بر اساس تراشهٔ DDR، یکی را انتخاب می‌کند:
> ```
> mem=256M ↔ mmz 72M   | mem=768M ↔ mmz 100M | mem=1G ↔ mmz 256M
> mem=1536M            | mem=2G ↔ mmz 380M   | mem=3840M ↔ mmz 600M
> ```
> پس **از روی فایل نمی‌توان رم واقعی را تعیین کرد** (این پلتفرم MV300 از بردهای تا ~4GB پشتیبانی می‌کند). تنها راه، خواندن روی خود دستگاه است:
> ```sh
> head -1 /proc/meminfo          # MemTotal واقعی
> dmesg | grep -i "Memory:"      # گزارش کرنل هنگام بوت
> ```
> به همین دلیل، منطق zram در اسکریپت **تطبیقی** طراحی شد و از `/proc/meminfo` می‌خواند — پس روی هر مقدار رمی درست کار می‌کند.



### ۴) تشخیص رم واقعی دستگاه — تابع `detect_ram()` (ریسک صفر)
برای دانستن رم واقعی **بدون حدس** و **بدون تغییر کد باینری** (طبق انتخاب گزینهٔ A):
- تابع `detect_ram()` هنگام بوت اجرا می‌شود و **فقط از `/proc` می‌خواند** و در `/data` و `/tmp` می‌نویسد — هیچ کار خطرناکی ندارد.
- محاسبهٔ کلیدی: **رم فیزیکی واقعی ≈ MemTotal + رزرو MMZ/CMA**. چون بخشی از رم برای پردازش تصویر رزرو می‌شود و در `MemTotal` لینوکس دیده **نمی‌شود** (مثلاً روی برد ۱GB معمولاً MemTotal حدود ۷۶۸MB است).
- خروجی در سه محل: `/data/raminfo.txt` (ماندگار)، `/tmp/raminfo.txt`، و لاگ کرنل (`dmesg`).

**چطور مقدار را ببینیم؟** (بعد از فلش و یک‌بار بوت)
```sh
cat /data/raminfo.txt        # ← ساده‌ترین راه؛ شامل MemTotal + رزرو + برآورد فیزیکی
# یا:
dmesg | grep -i "^RAM:"      # خط خلاصهٔ رم
head -1 /proc/meminfo        # MemTotal خام
```
> نمونهٔ خروجی `raminfo.txt`:
> ```
> MemTotal (MB)   : 768    # آنچه لینوکس می‌بیند
> MMZ/CMA reserved: 256MB
> Physical (est)  : 1024MB  # MemTotal + رزرو
> Rounded size    : 1024MB  # ← رم واقعی دستگاه
> ```
> اگر `Rounded size` مثلاً `2048MB` یا `4096MB` شد، یعنی رم واقعی ۲ یا ۴ گیگابایت است.

فایل `raminfo.txt` را برای من بفرستید تا مقدار قطعی رم را تأیید کنم.

## نکتهٔ مهم دربارهٔ فیلد flags و روش SAFE MODE
در جدول پارتیشن، فیلد چهارم rootfs مقدار `0x010FD868` دارد که با هیچ checksum استانداردی (crc32/crc24/sum/adler/xor) مطابقت نکرد و رمزگشایی قطعی نشد.
برای **صفر کردن ریسک brick**، rootfs جدید طوری ساخته شد که **کوچک‌تر یا مساوی اندازهٔ اصلی** باشد و سپس با صفر تا `img_len` اصلی pad شد. نتیجه:
> **هیچ فیلدی در هدر تغییر نکرد** (نه img_len، نه فیلد اندازهٔ 0x50، نه flags) → فایل از دید هر بررسی‌کنندهٔ هدر، معتبر و بدون تغییر ساختاری است. صفرهای انتهایی توسط gzip نادیده گرفته می‌شوند.

## ⚠️ هشدارهای فلش (حتماً بخوانید)

1. **این فایل روی سخت‌افزار واقعی تست نشده است.** درست بودن ساختار اثبات شده، اما رفتار زمان‌اجرا فقط روی دستگاه قابل‌تأیید است.
2. **حتماً backup کامل** از فریمویر فعلی و تنظیمات کاربری بگیرید (اگر رسیور گزینهٔ dump/backup دارد).
3. **مطمئن شوید مسیر بازیابی (rescue/USB recovery) دستگاه را می‌شناسید** پیش از فلش. مدل‌های HiSilicon معمولاً recovery از USB با فایل `*.mupg` در ریشهٔ فلش دارند.
4. اگر پس از فلش، zram مشکل‌ساز شد، چون در اسکریپت با `2>/dev/null` و شرط وجود ماژول محافظت شده، اثر مخرب نخواهد داشت؛ اما در بدترین حالت می‌توان با نسخهٔ اصلی دوباره فلش کرد.
5. **تست پیشنهادی روی دستگاه پس از فلش:**
   ```sh
   cat /proc/swaps            # باید zram0 دیده شود (اگر ماژول موجود بود)
   cat /proc/sys/vm/min_free_kbytes   # باید 16384 باشد
   ps | grep bianbiang        # باید زنده باشد؛ بعد از kill دستی باید خودکار برگردد
   ```
