# گزارش ممیزی پایداری فریمویر — Spider VIP v1.00.92

**تاریخ ممیزی:** 2026/07/09
**ممیز:** بازبینی مهندسی (Principal Embedded Linux Firmware Engineer mindset)
**پلتفرم:** HiSilicon Hi3798M V300 · Linux kernel 4.4.176 · Enigma2-based stack (`bianbiang`) · RAM: تشخیص خودکار تا 3840M (~3.75GB) — به بخش «تصحیح RAM» مراجعه شود

---

## 🔧 تصحیح مهم دربارهٔ حجم RAM (به‌روزرسانی پس از بررسی bootargs)

در نسخهٔ اول این گزارش عبارت «1GB RAM» به‌کار رفته بود که از رشتهٔ متادیتای هدر فایل `.mupg` (تگ `DDR 1GB`) برداشت شده بود. **بررسی دقیق‌ترِ متغیرهای محیطی U-Boot این را تصحیح می‌کند:**

فریمویر یک جدول کامل از پیش‌تنظیم‌های bootargs برای هر اندازهٔ DDR دارد و بوت‌لودر اندازهٔ واقعی رم را **خودکار تشخیص** می‌دهد:
```
bootargs_512M  = mem=512M  mmz=ddr,0,0,72M  vmalloc=500M
bootargs_768M  = mem=768M  mmz=ddr,0,0,72M  vmalloc=500M
bootargs_1G    = mem=1G    mmz=ddr,0,0,100M vmalloc=500M
bootargs_1536M = mem=1536M mmz=ddr,0,0,72M  vmalloc=500M
bootargs_2G    = mem=2G    mmz=ddr,0,0,100M vmalloc=500M
bootargs_3840M = mem=3840M mmz=ddr,0,0,72M  vmalloc=500M   ← پشتیبانی تا ~4GB
```

**نتیجه‌گیری قطعی:**
1. **ادعای سازندهٔ ۴GB لزوماً دروغ نیست.** فریمویر تا `3840M` (۳.۷۵GB قابل‌آدرس‌دهی — که همان ۴GB فیزیکی منهای ناحیهٔ رزرو سخت‌افزار است) را پشتیبانی می‌کند.
2. **فریمویر برای رم کمتر «اشتباه» برنامه‌نویسی نشده.** به‌جای مقدار ثابت، از auto-detect استفاده می‌کند و preset درست را انتخاب می‌کند.
3. برچسب `DDR 1GB` در هدر فقط یک **تگ نسخهٔ پکیج/متادیتا** است، نه محدودیت اجرایی.

**اما یک هشدار واقعی وجود دارد:** تشخیص درست رم به‌درستیِ **DTB و کد شمارش DDR در U-Boot** و نیز تراشه‌های حافظهٔ روی برد بستگی دارد. برای اطمینان قطعی، باید مقدار واقعی را **روی خود دستگاه** خواند (نه فقط از فایل فریمویر):
```sh
cat /proc/meminfo | grep MemTotal      # مقدار واقعی رم دیده‌شده توسط کرنل
cat /proc/cmdline                      # کدام mem= واقعاً اعمال شده
free -m
```
اگر `MemTotal` نزدیک ~۳.۶–۳.۸GB بود → ادعای ۴GB درست است. اگر ~۱GB بود → یا برد واقعاً ۱GB دارد (ادعای فروش نادرست)، یا auto-detect/DTB درست کار نمی‌کند و preset اشتباه انتخاب شده.

> **جمع‌بندی پاسخ به سؤال شما:** «فریمویر قفل‌شده روی ۱GB» **نیست**؛ تا ~۴GB را پشتیبانی می‌کند. تنها راه قطعیِ اثبات، خواندن `/proc/meminfo` روی دستگاه است — که هم ادعای سازنده را راستی‌آزمایی می‌کند و هم مشخص می‌کند آیا preset درست انتخاب شده یا نه.

## ⚠️ اعلام دامنه و صداقت روش‌شناختی (مهم — حتماً بخوانید)

پرامپت درخواستی یک **بازبینی خط‌به‌خط سورس C/C++** می‌خواهد. اما واقعیت فنی فایل فریمویر این است:

> **این فریمویر شامل کد منبع (source code) نیست.** محتوای پارتیشن rootfs، باینری‌های **کامپایل‌شده و strip‌شدهٔ ARM ELF** است (`/usr/bin/bianbiang` ~14MB، کتابخانه‌های Qt5، ماژول‌های netflix/youtube/kodi). هیچ فایل `.c`/`.cpp`/`.h` در rootfs وجود ندارد.

طبق اصل صریح خودِ پرامپت — **«هرگز حدس نزن؛ اگر شواهد کافی نیست صریحاً بگو؛ false negative بهتر از false positive»** — نمی‌توان دربارهٔ خطوط سورسی که وجود ندارند، use-after-free یا double-free یا missing-unlock گزارش کرد. هر ادعایی از آن دست، **جعل شاهد** خواهد بود.

### آنچه واقعاً قابل ممیزی است (و ممیزی شد):
| منبع شاهد | نوع | وضعیت |
|-----------|-----|-------|
| اسکریپت‌های شل (`bianbiang.sh`, init.d, rc*) | **سورس واقعی** | ✅ بازبینی خط‌به‌خط شد |
| `inittab` و سیاست supervise پروسه | **سورس واقعی** | ✅ بازبینی شد |
| `sysctl` / سیاست مدیریت حافظه کرنل | **کانفیگ واقعی** | ✅ بازبینی شد |
| ساختار پارتیشن و منابع سیستم | متادیتا | ✅ بررسی شد |
| باینری `bianbiang` (منطق داخلی C++) | باینری strip | ⛔ نیازمند مهندسی معکوس (Ghidra/IDA) — خارج از دامنهٔ استخراج فعلی |

بنابراین این گزارش، یافته‌های **قطعی و مبتنی بر شاهد** را از لایهٔ سیستم/راه‌اندازی/کرنل ارائه می‌دهد که دقیقاً همان لایه‌ای است که مسئول «هنگ طولانی‌مدت، عدم بازیابی پس از crash، و فریز» است — و برای لایهٔ باینری، مسیر ادامهٔ کار (مهندسی معکوس) را مشخص می‌کند.

## ۱. خلاصهٔ اجرایی (Executive Summary)

سیستم یک استک Enigma2 روی HiSilicon است. **مهم‌ترین یافته این نیست که برنامه memory leak دارد یا نه؛ مهم‌ترین یافته این است که سیستم هیچ سازوکار بازیابی (recovery/supervision) ندارد.** یعنی هر علتی که باعث خروج یا کشته‌شدن اپلیکیشن اصلی شود — چه memory leak، چه crash، چه OOM-kill، چه deadlock — به **صفحهٔ سیاه دائمی تا خاموش/روشن دستی** منجر می‌شود، چون:

1. `inittab` اپ را با اکشن **`once`** اجرا می‌کند، نه `respawn`.
2. `bianbiang.sh` هیچ **حلقهٔ راه‌اندازی مجدد** ندارد؛ حتی exit code مخصوص «restart» (کد ۳) عملاً بی‌اثر است.
3. سه سرویس پس‌زمینهٔ حیاتی بدون هیچ نظارتی رها می‌شوند.

این ترکیب باعث می‌شود «هنگ کردن رسیور» که کاربر گزارش کرده، **صرف‌نظر از علت ریشه‌ای**، غیرقابل‌بازیابی خودکار باشد. علاوه بر این، پیکربندی حافظهٔ کرنل روی دستگاه ۱GB **بدون swap/zram** و با رزرو حافظهٔ بسیار پایین، ریسک OOM را در uptime طولانی بالا می‌برد.

## ۲. یافته‌های قطعی (Confirmed Findings)

### 🔴 ISSUE-001 — نبود Supervision/Respawn برای اپلیکیشن اصلی
- **Severity:** Critical | **Confidence:** High
- **Category:** Process lifecycle / Recovery
- **File:** `/etc/inittab` خط ۴۲ و `/usr/bin/bianbiang.sh`
- **Snippet:**
  ```
  gui:3:once:/usr/bin/bianbiang.sh
  ```
  ```sh
  # bianbiang.sh
  /usr/bin/bianbiang
  ret=$?
  case $ret in
      3) ;;        # "restart enigma" ← بدنه خالی! هیچ کاری نمی‌کند
      45) ;;       # خالی
      42) ;;       # خالی
  esac
  ```
- **Root cause:** اکشن `once` در inittab یعنی init پس از پایان پروسه، آن را دوباره اجرا نمی‌کند. اسکریپت هم برای کد خروج ۳ (که خودِ کامنت آن را «restart enigma» می‌نامد) هیچ اقدامی ندارد و حلقه‌ای دور اجرای `bianbiang` نیست.
- **چرا خطرناک است:** هر خروج غیرمنتظره (crash / OOM-kill / assert / signal) = صفحهٔ سیاه دائمی. دستگاه «هنگ» به نظر می‌رسد در حالی که کرنل زنده است ولی UI مرده و بازنمی‌گردد.
- **علائم زمان اجرا:** بعد از چند ساعت/روز استفاده، تصویر می‌رود و ریموت پاسخ نمی‌دهد؛ فقط قطع‌ووصل برق درست می‌کند.
- **بدترین حالت:** غیرقابل‌استفاده‌شدن دستگاه تا مداخلهٔ دستی کاربر.
- **احتمال ایجاد:** freeze ✔️بالا، hang ✔️بالا (این دقیقاً الگوی علامت گزارش‌شده است).
- **Fix پیشنهادی (سورس شل — کم‌ریسک):**
  ```sh
  # bianbiang.sh — قرار دادن اجرای اپ داخل حلقهٔ نظارتی
  while true ; do
      /usr/bin/bianbiang
      ret=$?
      case $ret in
          1) /sbin/halt ;;
          2) /sbin/reboot ;;
          3|42|45) sleep 1 ; continue ;;   # restart داخلی
          43) /usr/bin/ofgwrite ; init 1 ;;
          *) sleep 2 ; continue ;;          # هر خروج غیرمنتظره → راه‌اندازی مجدد
      esac
      break
  done
  ```
- **چرا درست است:** هر مسیر خروج غیرنهایی به راه‌اندازی مجدد UI ختم می‌شود و دستگاه خودش را بازیابی می‌کند به‌جای هنگ دائمی. `sleep` از حلقهٔ crash پرسرعت (busy-restart) جلوگیری می‌کند.
- **Side effect:** اگر crash ریشه‌ای رخ دهد، به‌جای صفحهٔ سیاه، یک فلش کوتاه و بازگشت به منو دیده می‌شود (بسیار بهتر برای کاربر). لازم است لاگ‌گیری خروج اضافه شود تا علت ریشه‌ای بعداً پیدا شود.

### 🔴 ISSUE-002 — سرویس‌های پس‌زمینه بدون نظارت
- **Severity:** High | **Confidence:** High
- **Category:** Process lifecycle
- **File:** `/usr/bin/bianbiang.sh` خطوط ۸، ۱۰، ۱۱
- **Snippet:**
  ```sh
  /usr/bin/satipclient &
  /usr/bin/app_console "/tmp/console_server_fifo" "/tmp/console_resp_fifo" &
  /usr/bin/streamrelay &
  ```
- **Root cause:** سه سرویس با `&` در پس‌زمینه اجرا می‌شوند و PID آن‌ها ذخیره یا مانیتور نمی‌شود. اگر هرکدام crash کند، هرگز بازراه‌اندازی نمی‌شود.
- **چرا خطرناک است:** `streamrelay` (رله جریان) و `satipclient` (SAT>IP) اگر بمیرند، پخش شبکه/IPTV به‌تدریج قطع می‌شود بدون آنکه اپ اصلی متوجه شود → «playback failure» تدریجی.
- **علائم:** برخی کانال‌های شبکه/IPTV پس از مدتی کار نمی‌کنند، اما منو کار می‌کند.
- **احتمال:** playback failure ✔️، resource-leak جزئی (fifo/socket یتیم) ✔️.
- **Fix:** استفاده از یک supervisor سبک (مثلاً حلقهٔ نظارتی جدا یا `runit`/`busybox` respawn در inittab برای هر سرویس) یا حداقل بررسی دوره‌ای PID و restart.

### 🟠 ISSUE-003 — پیکربندی حافظهٔ کرنل نامناسب برای uptime طولانی (بدون swap)
- **Severity:** High | **Confidence:** High
- **Category:** Memory management / Resource exhaustion
- **File:** `/etc/sysctl.conf`
- **Snippet:**
  ```
  vm.min_free_kbytes = 8192      # فقط ۸MB رزرو روی دستگاه ۱GB
  vm.swappiness     = 30         # اما هیچ swap/zram فعال نیست → بی‌اثر
  vm.dirty_ratio    = 60         # بسیار بالا
  vm.dirty_background_ratio = 1
  ```
  - تأیید شد: هیچ `zram`/`mkswap`/swap-partition فعالی وجود ندارد (فقط `swapon -a` روی fstab خالی از swap).
- **Root cause چندگانه:**
  1. **`min_free_kbytes=8192` بسیار پایین است.** روی ۱GB با مصرف سنگین Qt5+WebKit+decoder، رزرو ۸MB می‌تواند در فشار حافظه منجر به allocation-stall و فعال‌شدن OOM-killer شود.
  2. **نبود swap/zram:** هیچ سوپاپ اطمینانی برای فشار حافظه نیست. با کوچک‌ترین رشد مصرف (leak یا fragmentation)، مسیر مستقیم به OOM-kill است — که طبق ISSUE-001 غیرقابل‌بازیابی است.
  3. **`dirty_ratio=60`:** اجازه می‌دهد تا ۶۰٪ RAM صفحات dirty انباشته شود؛ هنگام ضبط/تایم‌شیفت روی USB کند، flush ناگهانی می‌تواند **write-stall و فریز کوتاه UI** ایجاد کند.
- **چرا خطرناک است:** این پیکربندی، سیستم را در برابر هر رشد حافظه‌ای شکننده می‌کند و مسیر «فشار حافظه → OOM-kill اپ → صفحه سیاه (ISSUE-001)» را کوتاه می‌کند.
- **احتمال:** memory-exhaustion freeze ✔️، write-stall hang ✔️.
- **Fix پیشنهادی (کانفیگ — کم‌ریسک، قابل اعمال بدون تغییر باینری):**
  ```
  vm.min_free_kbytes = 16384          # افزایش رزرو به ۱۶MB
  vm.swappiness = 0                   # بدون swap، صفر منطقی‌تر است
  vm.dirty_ratio = 20                 # کاهش سقف dirty برای جلوگیری از stall
  vm.dirty_background_ratio = 5
  vm.overcommit_memory = 0
  ```
  و افزودن **zram** به‌عنوان swap فشرده در RAM (به‌جای USB) در یک اسکریپت init:
  ```sh
  modprobe zram num_devices=1
  echo lz4 > /sys/block/zram0/comp_algorithm
  echo 256M > /sys/block/zram0/disksize
  mkswap /dev/zram0 && swapon -p 100 /dev/zram0
  ```
- **چرا درست است:** zram یک سوپاپ اطمینان فشرده در RAM می‌دهد که پیش از OOM-kill، صفحات کم‌استفاده را فشرده می‌کند و عمر پایداری را در فشار حافظه بالا می‌برد؛ کاهش dirty_ratio از فریزهای I/O جلوگیری می‌کند.
- **Side effect:** zram کمی CPU مصرف می‌کند (روی Cortex-A53 ناچیز). این‌ها **درمان علامت** هستند، نه رفع leak ریشه‌ای در باینری.

### 🟡 ISSUE-004 — نبود سازوکار نگهداری حافظه/کش در uptime طولانی
- **Severity:** Medium | **Confidence:** High
- **Category:** Long-uptime maintenance
- **شاهد:** هیچ `cron`، هیچ استفاده از `drop_caches`، و هیچ تسک نگهداری دوره‌ای در rootfs یافت نشد.
- **Root cause:** سیستم هیچ نگهداری پیشگیرانه‌ای (پاکسازی `/tmp`، آزادسازی کش، چرخش لاگ) ندارد. `/tmp` و `/data/bianbiang.log` (در حالت debug) می‌توانند بی‌حد رشد کنند.
- **چرا خطرناک است:** در uptime هفتگی، انباشت فایل موقت/لاگ روی tmpfs (که RAM مصرف می‌کند) به فشار حافظه اضافه می‌کند.
- **احتمال:** slow resource growth ✔️.
- **Fix:** افزودن یک cron سبک برای چرخش لاگ و پاکسازی `/tmp`، و در صورت نیاز drop_caches دوره‌ای محافظه‌کارانه.

### 🟡 ISSUE-005 — باگ کپی‌پیست در مسیر پاکسازی USB unmount
- **Severity:** Low | **Confidence:** High
- **Category:** Error handling / cleanup
- **File:** `/usr/bin/bianbiang.sh` خطوط ۸۴–۹۵
- **Snippet:**
  ```sh
  if [ -e /tmp/UD1 ];then umount /tmp/UD1 ; rm /tmp/UD0 ; fi   # ← باید UD1 حذف شود
  if [ -e /tmp/UD2 ];then umount /tmp/UD2 ; rm /tmp/UD0 ; fi   # ← باید UD2
  if [ -e /tmp/UD3 ];then umount /tmp/UD3 ; rm /tmp/UD0 ; fi   # ← باید UD3
  ```
- **Root cause:** در هر سه شاخه، به‌اشتباه `rm /tmp/UD0` نوشته شده (کپی‌پیست). نقاط mount `UD1/UD2/UD3` پس از umount حذف نمی‌شوند و `UD0` چند بار حذف می‌شود.
- **چرا مهم است:** نقاط mount یتیم در `/tmp` باقی می‌مانند؛ در طول زمان و اتصال/قطع مکرر USB، انباشت entry و احتمال خطای mount بعدی.
- **احتمال:** resource leak جزئی (mount points یتیم) ✔️.
- **Fix:** اصلاح به `rm /tmp/UD1`، `rm /tmp/UD2`، `rm /tmp/UD3` در شاخه‌های متناظر.

## ۵. مهم‌ترین علت محتمل «هنگ طولانی‌مدت رسیور»

بر اساس **شواهد قطعی موجود**، محتمل‌ترین توضیح این است:

> یک رشد منبع در `bianbiang` (leak حافظه یا fd — که هنوز در سطح باینری اثبات نشده) به‌مرور RAM محدود ۱GB را پر می‌کند؛ چون **swap/zram وجود ندارد و min_free بسیار پایین است (ISSUE-003)**، OOM-killer اپ را می‌کشد؛ و چون **هیچ respawn وجود ندارد (ISSUE-001)**، دستگاه در صفحهٔ سیاه دائمی هنگ می‌کند.

نکتهٔ کلیدی: حتی اگر leak ریشه‌ای در باینری باشد، **ISSUE-001 و ISSUE-003 آن را به یک هنگ غیرقابل‌بازیابی تبدیل می‌کنند**. رفع این دو (که سورس/کانفیگ در دسترس‌اند) بیشترین بهبود پایداری را با کمترین ریسک می‌دهد.

## ۷. تأیید‌شده در برابر مشکوک

- **تأیید‌شده (High Confidence، شاهد مستقیم):** ISSUE-001، 002، 003، 004، 005 — همگی از فایل‌های متنی/کانفیگ واقعی استخراج شدند.
- **مشکوک/تأیید‌نشده (نیازمند شاهد بیشتر):** هر ادعای leak/UAF/deadlock در منطق داخلی `bianbiang` و کتابخانه‌ها. این‌ها **عمداً گزارش نشدند** تا اصل «false negative بهتر از false positive» رعایت شود.

---

## ۸. نواحی نیازمند بازبینی دستی (گام بعدی)

برای پاسخ قطعی به بخش‌های «Memory Management / Concurrency / Multimedia pipeline» پرامپت، باید باینری‌ها مهندسی معکوس شوند:

1. **`/usr/bin/bianbiang`** (اپ اصلی): بارگذاری در Ghidra، تحلیل مسیرهای `malloc/free`، چرخهٔ decoder، channel-switch، EPG refresh.
2. **`streamrelay`, `satipclient`, `app_console`**: تحلیل مدیریت socket/fd.
3. **بررسی زنده (اگر دستگاه در دسترس باشد):** فعال‌کردن `/data/enable_debug`، اجرای دستگاه، و پایش `cat /proc/<pid>/status | grep VmRSS` در بازه‌های زمانی برای اثبات یا رد رشد حافظه — این **قطعی‌ترین** راه اثبات memory leak است و به سورس نیاز ندارد.

> پیشنهاد عملی: قبل از هر مهندسی معکوس پرهزینه، **تست زندهٔ VmRSS** روی خود دستگاه بهترین گام است؛ اگر رشد پایدار حافظه دیده شد، leak اثبات می‌شود و بعد سراغ باینری می‌رویم.
