# موضوع: وصلهٔ رسیور (Receiver patches)

صفحهٔ کنسول `/patches/` برای نصب، حذف و دیدن وضعیت افزونه‌هایی که روی خود رسیور اجرا می‌شوند.
این افزونه‌ها در `/data` نصب می‌شوند و از `/home/gx/local/user_script` (که `bianbiang.sh` هنگام هر روشن شدن اجرا می‌کند)
شروع می‌شوند. **به‌روزرسانی firmware یا Reset to Factory آن‌ها را پاک می‌کند** — بعد از آن، همین صفحه «نصب نیست» نشان می‌دهد
و با یک کلیک دوباره نصب می‌شوند.

- کد: [`../../spidervip/patches/`](../../spidervip/patches/) — `framework.py` (نصب/حذف/وضعیت)، `registry.py` (فهرست وصله‌ها)، `webapp.py`
- اجرا: کنسول (`RUN.bat`) → «وصلهٔ رسیور»

## هر وصله

| بخش | معنی |
|---|---|
| فایل‌ها | با gzip + base64 روی Telnet کپی می‌شوند، md5 بررسی می‌شود، جایگزینی اتمیک (tmp + mv) |
| اجرای خودکار | یک خط برچسب‌دار در `user_script`؛ حذف فقط همان خط را پاک می‌کند |
| شروع/توقف | `setsid` برای شروع؛ توقف فقط نسخهٔ همین boot (pid + boot_id) |
| وضعیت | نصب/نیمه‌نصب، در حال اجرا (pid)، به‌روز بودن (md5 فایل روی رسیور در برابر PC)، آخرین خطوط گزارش |
| حذف | پرچم disable، توقف، حذف خط `user_script`، پاک کردن پوشهٔ وصله (فقط زیر `/data/` و نه خود `/data` یا `/data/gx`) |

## وصله‌ها

1. **نگهبان فریز صوتی** (`tools/audio_watch.sh` → `/data/audio_watch/`) — آماده. خط اجرای خودکار همان است که
   `tools/deploy_audio_watch.py` و `PATCH_RECEIVER.bat` می‌نویسند، پس هر دو روش با هم سازگارند.
   بعد از رفع ریشهٔ فریز با «حذف» برداشته می‌شود.
2. **به‌روزرسانی خودکار فرکانس** — **فاز ۱: فقط گزارش** (آماده). فایل‌ها در `/data/spidervip_freq_auto/`:
   - `loop.sh` — زمان‌بند: صبر تا تنظیم ساعت با NTP (کف `min_epoch` = زمان نصب منهای یک روز)، سپس هر `interval_s`
     (پیش‌فرض ۷ روز) یک بار `runner.py` را با `nice -n 19` اجرا می‌کند؛ اجرای ناموفق ۶ ساعت بعد تکرار می‌شود. pid با boot_id.
   - `runner.py` — با Python 3.9 خود رسیور و `freqcore/` (کپی همان `spidervip/frequency/core`): لیست OpenPLi را از GitHub می‌گیرد،
     با satellites.xml و lamedb رسیور مقایسه می‌کند و `last_report.json` می‌نویسد. **هیچ چیزی را روی رسیور تغییر نمی‌دهد.**
     قفل `run.lock` از اجرای هم‌زمان جلوگیری می‌کند. آزمایش‌شده روی رسیور (۲۰۲۶-۱۱-۱۱): Python 3.9.7، ۲۳ ثانیه، بدون خطا.
   - در صفحه: «اجرای فوری» (در پس‌زمینهٔ رسیور) و «نمایش گزارش» (خلاصه + ماهواره‌های پرتغییر).

   **فاز ۲: اعمال خودکار (ساخته شد، ۲۰۲۶-۱۱-۱۱؛ هنوز روی رسیور نصب نشده).** تصمیم‌های مالک: هر ۷ روز، فقط بعد از ساعت ۱۲ شب
   (۰۰:۰۰ تا ۰۶:۰۰)، با هر تعداد تغییر؛ همهٔ اصلاح‌ها و TPهای جدید؛ **حذف TPهایی که در منبع نیستند، به‌جز TPهای دارای کانال**
   («روش ۱»، تصمیم مالک پس از کشف زیر) — این‌ها فقط در گزارش به‌عنوان «نامزد حذف» با نام کانال‌هایشان می‌آیند؛ برگشت خودکار در صورت شکست؛
   بدون هشدار جداگانه. (کد حذف TP همراه کانال‌ها از lamedb/Favoriteها — `lamedb.remove_transponders` / `filter_bouquet` — برای «روش ۳»
   یعنی حذف فقط TPهایی که قبلاً در منبع بوده‌اند و رفته‌اند، نگه داشته شده است؛ در runner خاموش است: `DELETE_CHANNEL_TPS = False`.)
   - `runner.py apply`: snapshot (`/data/spidervip_freq/snap_auto_*`)، نوشتن satellites.xml / lamedb / userbouquet، 
     `servicelistreload` روی `127.0.0.1`، برگرداندن Motor در live_prog، ثبت `pending.json` و `reboot -f`.
     کانال روی TPای که کلید `ns:tsid:onid` را با TP ماندگار شریک است حذف نمی‌شود (مالکش مشخص نیست).
   - پس از روشن شدن، `loop.sh` بعد از ۹۰ ثانیه `runner.py verify` را اجرا می‌کند: لیست TP دقیقاً مطابق برنامه، کانال‌های یکتا ≥ انتظار
     (پس از حذف عمدی)، Motor همهٔ ماهواره‌ها. اگر یکی درست نبود: برگشت کامل به snapshot، `reboot -f`، و در boot بعد بررسی برگشت.
     برگشت فقط یک بار انجام می‌شود؛ تا تأیید تمام نشده اعمال تازه‌ای شروع نمی‌شود.
   - گزارش (`last_report.json`) نتیجه (`applied` / `rolled_back` / `nothing` / `error_restored`) و نام کانال‌هایی را که همراه TPها حذف
     می‌شوند نشان می‌دهد — در حالت گزارش هم، تا قبل از اعمال دیده شوند.
   - **نکته (۲۰۲۶-۱۱-۱۱):** گزارش واقعی نشان داد فاز ۲ چهار TP روی Badr 26E (11046 H، 11547 V، 11604 H، 11623 V) را با ۲۲ کانال
     (خانوادهٔ Al Jazeera، شبکه‌های مراکش، Arryadia) و ۱۲ خانهٔ Favorite حذف می‌کند. **لیست OpenPLi درست است:** این ۴ TP روی
     **Es'hail 1 در 25.5E** هستند (در منبع و در satellites.xml خود رسیور زیر 25.5E هم هستند). دیش روی 26E، ماهوارهٔ 25.5E را هم
     می‌گیرد، پس این کانال‌ها هنگام اسکن زیر 26.0E ذخیره شده‌اند (namespace `0104` در lamedb؛ هیچ کانالی زیر 25.5E = `00ff` نیست)
     و پخش می‌شوند. حذف آن TPها از 26.0E این ۲۲ کانال را پاک می‌کرد، با اینکه از هوا نرفته‌اند. پس «در منبع زیر این ماهواره نیست» همیشه
     یعنی «از هوا رفته» نیست → روش ۱. (پیش‌نویس issue برای OpenPLi ثبت نشد؛ ایرادی در لیست آن‌ها نبود.)
   - **برچسب «ماهوارهٔ همسایه» (۰٫۱۴٫۲):** برای هر نامزد حذف، `satxml.nearby_tps` همین فرکانس (همان قطبش به شکل رسیور، ±۳ MHz) را روی
     ماهواره‌های دیگرِ منبع در فاصلهٔ حداکثر ۱٫۰ درجه می‌گردد و در گزارش (`candidates.tps[].nearby`) و صفحه نشان می‌دهد؛
     مثلاً «در منبع روی 25.5E Es'hail 1 هست». این فقط برچسب است و رفتار اعمال را عوض نمی‌کند.

## افزودن وصلهٔ تازه

یک `Patch` در `spidervip/patches/registry.py` تعریف کنید (پوشه زیر `/data/`، فایل‌ها، برچسب و خط `user_script`، فرمان شروع،
فایل pid و گزارش) و به `PATCHES` اضافه کنید؛ صفحه و API خودکار آن را نشان می‌دهند.

## API (زیر `/patches/` در کنسول)

| مسیر | کار |
|---|---|
| `GET /api/patches` | فهرست وصله‌ها |
| `POST /api/status` `{host,user,password}` | وضعیت همهٔ وصله‌های آماده روی رسیور (فقط خواندن) |
| `POST /api/install` `{host,…,id}` | نصب یا به‌روزرسانی |
| `POST /api/remove` `{host,…,id}` | حذف |
| `POST /api/run` `{host,…,id}` | اجرای فوری کار یک‌بارهٔ وصله در پس‌زمینهٔ رسیور |
| `POST /api/report` `{host,…,id}` | آخرین گزارش وصله (مثلاً `last_report.json`) |
