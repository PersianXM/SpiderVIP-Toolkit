# گزارش تحلیل هنگ دستگاه — ۲۰۲۶/۰۷/۱۱ (نسخهٔ قطعی، مبتنی بر forensic بعد از بوت)

## خلاصهٔ اجرایی
دستگاه حین جلسه کاملاً هنگ کرد و از شبکه محو شد (`Destination host unreachable`) و
**خودبه‌خود برنگشت**؛ با دکمهٔ power خاموش/روشن شد. پس از بوت، چهار کپچر forensic زندهٔ
`/proc` گرفته شد. نتیجه:

> **علت هنگ، کار ما (overlay فریم‌بافر `dbgbar`) نبود.** در زمان بررسی `dbgbar` اصلاً در
> حال اجرا نبود. فرضیهٔ اولیهٔ حرارتی هم **با داده رد شد**. مقصرِ واقعیِ بار سیستم،
> **زیرسیستم USB gadget (udisk + استریم TS به‌نام gservice)** است که کل خط‌لولهٔ ویدئوی
> HiSilicon را در صف رویداد نگه می‌دارد.

## شواهد (چهار کپچر)

### حرارت — رد شد
```
Chip Temperature : 75
up threshold: 100 | reboot threshold: 125
```
۷۵° هیچ نزدیکیِ به تریپ ندارد. dmesg هم هیچ `thermal`/`panic`/`lockup`/`oom` ندارد.

### پارادوکس load بالا با CPU بیکار
```
load average: 14.40  (nproc = 4)
%Cpu(s): 89.7 id      <-- CPU در واقع بیکار
```
load بالا از شمرده‌شدن نخ‌های **D-state (uninterruptible sleep)** می‌آید، نه اشباع CPU.

### نخ‌های D-state — همه از خانوادهٔ ویدئو + USB
```
D 651  usb-otg           wchan = msleep
D 908  g_udisk_task      wchan = msleep
D 1008 HI_VPSS_Logic
D 1009 HI_VPSS_Softwar   wchan = VPSS_OSAL_WaitEvent
D 1012 HI_VDEC_Task
D 951  HI_HDMI_kThread
D 952  DispProcess
```
`VPSS_OSAL_WaitEvent` و `msleep` یعنی این نخ‌ها **منتظر رویداد سخت‌افزاری/تایمر** هستند
(رفتار عادی درایور)، نه قفل مرده. اما دائماً در D شمرده می‌شوند و load را بالا نگه می‌دارند.

### storm وقفهٔ USB gadget — بار واقعی و پایدار
```
dwc_otg_pcd IRQ: 125246 -> 126834 در 5s  ≈ 318 وقفه/ثانیه
dmesg: 391x  "service gadget: non-core control req23.03 ... l516"
       gservice_ts_thread: read ~31208 bytes  (رنگ قرمز = مسیر خطا/هشدار)
```
یک دستگاه USB (udisk gadget) وصل است و درایور دائماً درخواست‌های control و خواندن TS را
پردازش می‌کند. این پرترافیک‌ترین و تنها بار غیرعادیِ سیستم است.

### وضعیت پایداری فعلی
```
load: 14.35 -> 14.40 در 5s  => تثبیت‌شده، در حال فرار (runaway) نیست
dbgbar NOT running          => overlay ما در ماجرا دخیل نیست
```

## نتیجه‌گیری علت ریشه‌ای
۱. **overlay ما (dbgbar) تبرئه شد** — هنگام هنگ اجرا نبود و الان هم اجرا نیست.
۲. **حرارت تبرئه شد** — ۷۵° در برابر آستانهٔ ۱۲۵°، dmesg تمیز.
۳. **مقصر: زیرسیستم USB gadget** — udisk/gservice با ~۳۱۶ وقفه بر ثانیه و سیل درخواست‌های
   control. این بار سنگین I/O، نخ‌های VPSS/VDEC/HDMI را در حالت انتظار (D) انباشته می‌کند.
   یک قفل/بن‌بست در مسیر `usb-otg ↔ udisk ↔ gservice_ts_thread` می‌تواند کل SoC را به
   بن‌بست ببرد و چون این نخ‌ها RT/کرنلی‌اند، حتی شبکه هم می‌میرد و watchdog یوزراسپیس
   (`bianbiang.sh`) بی‌اثر می‌شود — دقیقاً علامتی که دیدیم.

> این با تجربهٔ شناخته‌شدهٔ این پلتفرم می‌خواند: **استریم TS روی USB gadget زیر بار،
> نقطهٔ‌ضعف پایداری این فریمویر است** (نه حرارت، نه overlay).

## توصیه‌ها
### فوری (عملیاتی)
- اگر از **خروجی TS روی USB (PC-Link/PVR-over-USB)** استفاده نمی‌کنید، آن را در منوی
  رسیور غیرفعال کنید؛ storm وقفهٔ gservice قطع می‌شود.
- کابل/هاب USB و کیفیت تغذیه را بررسی کنید؛ storm درخواست control گاهی از لینک USB بی‌کیفیت
  می‌آید.

### برای نسخهٔ customize فریمویر
- در `bianbiang.sh`: افزودن ناظر سبک که اگر نرخ وقفهٔ `dwc_otg` از آستانه (مثلاً >۲۵۰/ثانیه)
  برای Nثانیهٔ متوالی بالا ماند، `gservice`/gadget را کنترل‌شده ری‌استارت کند (به‌جای هنگ کل SoC).
- در `providers.c` (dbgbar): همین حالا `irq_rate` گجت را می‌سنجیم؛ اضافه‌کردن آستانهٔ
  هشدار «USB:STORM» تا اپراتور پیش از هنگ ببیند.
- در داشبورد PC: قانون تحلیل ریشه‌ای «USB gadget interrupt storm» اضافه شود تا این الگو
  (load بالا + CPU بیکار + نرخ dwc_otg بالا) خودکار پرچم بخورد.
